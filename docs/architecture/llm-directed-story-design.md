# 剧情导演与LLM会话分离：初步设计

2026-11-01，v0.1，待用户审阅。本轮只新增设计稿与文档入口，不修改运行中的剧情、协议、Graph或前端交互。

## 目标和当前问题

当前3.0.0把长篇创作稿落实为76个逐句推进节点。manifest包含133条预写台词、117条玩家发言和85条导演提示；其中许多“推荐”只是执行下一节点的入口。即使LLM生成了行动推荐，过滤器仍可能用playerReplies覆盖原句。

本设计把这部分改为：作者约束人物、事实、段落目的和合法事件；LLM根据真实上下文生成普通对白与玩家回复推荐。仍然使用现有真实TTS、播放队列、事件回执与取消边界。不会增加Mock语音、text.ready或新的文字替代通道。

## 玩家能感受到的变化

| 当前                             | 拟调整后                                         |
| -------------------------------- | ------------------------------------------------ |
| 不同用户看到相同的“下一句”       | 根据刚才实际说过、听过的话生成候选               |
| 点推荐可直接提交预绑定动作       | 点推荐只发送它的文字，和手打/语音走相同意图校验  |
| 一句预写玩家话对应一句预写角色话 | 同一场景能接住不同表达、解释和话题               |
| 76个逐句节点构成主要节奏         | 两次见面的16场戏构成骨架，每场可有不同长度的交流 |
| 经常出现同一句“我还想多聊一会儿” | 停留、玩笑、分享、探索等候选由当前回应自然产生   |
| 部分自由聊天像从主线暂时绕开     | 交流本身就是场景内容；换话题不需要切换模式       |

独处/黑场中的“等待、继续观看、结束”仍是明确的呈现操作，不冒充玩家台词或LLM推荐。保持现有位置与视点分离，玩家不会因看见补妆镜头而被记为跟进洗手区。

## 内容文件怎样拆

| 文件                                                            | 拟保留的职责                                         | 拟移除或迁出的内容                                                        |
| --------------------------------------------------------------- | ---------------------------------------------------- | ------------------------------------------------------------------------- |
| `scenario/cafe/manifest.json`                                   | 包ID/版本、入口、资源、呈现配置、能力和内容引用      | playerReplies、固定chatReplies、大量逐句voices和按每句分配的directorNotes |
| `scenario/cafe/character.json`                                  | 身份、口吻、主动性、边界                             | 不把整部未来剧情塞进人设                                                  |
| `scenario/cafe/lore.json`                                       | 世界真相、人物背景、固定信件、知情条件               | 不把LLM猜测或玩家未确认的经历写成真相                                     |
| 拟新增 `scenario/cafe/chapters.json`                            | 16场戏的目的、话题机会、可用事件、退出条件和节奏提示 | 不定义玩家下一句必须怎么说                                                |
| `main.ink`、`first-night.ink`、`second-date.ink`、`endings.ink` | 关键事件、分支合法性、事实变化、可恢复checkpoint     | talk-a01-1这类逐句推进，不再一句一句解锁对白                              |
| 现有剧情设计稿                                                  | 创作参考、可选例句、节奏与支线素材                   | 不把所有例句当作运行时必播内容                                            |

保留少量固定文本：必要开场、固定道具正文、必须准确公开的短事实锚点，以及确定性转场。它们和普通可生成的对白要有明确标记，不再混在一个庞大的voices目录里。

初稿不新建完整创作平台，也不更换Ink、LangGraph或Provider体系。

## 一场戏如何描述

以“补妆前”为例，以下是拟议内容形状，不是当前已经支持的schema：

```json
{
  "id": "first-night.before-makeup",
  "purpose": "她愿意暂时卸下从容，给这段交流留一个回来继续的机会",
  "focus": ["刚才没接好的话", "她也会紧张", "玩家是否愿意继续聊"],
  "availableFacts": ["mira.off-duty"],
  "opportunities": ["clarify-misunderstanding", "offer-a-short-break"],
  "exitActions": ["wait-at-seat", "wait-nearby", "say-goodnight"],
  "constraints": [
    "没有选择前，不说玩家已经答应等候",
    "不宣称恋爱、共度一夜或其他尚未确认的关系",
    "她独处的心声不等于玩家在现场听见"
  ],
  "pacing": "有一次相互表达的空间；用户明确想离开时不强留"
}
```

这些键只提供约束和交流机会。LLM可以幽默地说、坦白地说，也可以先接住玩家自己的经历；不能把这份配置逐条念给玩家。

后端加载时校验ID、事实引用、合法动作、长度和容量。与场景无关的内容不进入公共Graph或前端关键词判断。

## 每轮怎样工作

### 普通交流

1. 取得已确认的剧情快照与当前段落。
2. 组装人物、当前可知内容、当前场景目的、近期已确认对话、当前合法动作。
3. 一次LLM调用同时产生角色回应和2–3条可选玩家发言；允许少给或不给。
4. 校验结构、长度、动作引用和事实边界；不把候选替换成作者固定句子。
5. 真实TTS只朗读角色对白；旁白、心声走现有叙事呈现能力。
6. 全部实际呈现完成后才显示候选；用户点选后按普通文字输入重新解释。

推荐生成本身不表示用户发言、同意、行动或剧情完成。历史裁剪不丢掉已确认的世界事实；仍不引入好感分或按聊天轮数自动升级关系。

### 请求移动、读信或其他关键事件

1. LLM从当前合法动作里解释用户请求；关键动作继续进行独立明确意图复核。
2. Ink提议事件，播放器按依赖执行，服务端等待实际呈现回执。
3. 事件确认后，按新的已知状态生成自然承接和下一句推荐，不能继续拿事件前的候选凑数。
4. 若动作失败、中断、用户又发了一句或revision改变，丢弃旧的后续生成，不提交状态或展示旧推荐。

**调用成本的明确变化**：普通聊天通常一次模型调用；事件路径可能增加一次“事件后的角色回应＋推荐”调用；关键明确意图复核沿用现有额外调用。不能承诺所有路径都只调用一次。初稿优先避免提前泄露新事实，不另设推荐专用模型，也不为凑满候选循环调用。

### 首屏

建议保留作者定义的一句开场，先展示输入。第一轮实际回应后开始显示LLM推荐，不再塞预写playerReplies。

如果产品必须首屏就有动态推荐，需要增加一次会话初始化模型请求；在本初稿中列为可选项，不默认引入新的后台初始化任务。

## 对白、旁白和心声

- 普通对白由LLM根据本次交流生成，真实TTS与字幕使用同一份文本。
- 普通观察旁白与短心声可以动态生成，但要独立字段校验，不能夹在对白中一起朗读。
- 新增字段优先放在私有Planner输出中；网络呈现复用已有presentation.ready和caption，不新增text.ready或独立聊天入口。
- 必须准确的道具、短事实锚点和转场旁白继续由作者定义。
- 心声只能表达她自己的迟疑、期待或观察，不能替玩家认定感受，也不能作为玩家已经听见或已经同意的证据。
- 独处片段保留确定性分镜、作者心声与实际呈现回执；初稿不让模型在她独处时假装听见玩家隔空发言。

结构校验不能证明每句自然语言都不暗示新事实。依靠最小知情上下文、受控事件锚点、失败时不给候选，以及多轮验证降低偏移；不宣称“加了JSON schema就保证完全不脱节”。

## 推进条件怎样掌握

需要区分三件事：聊到一个话题、提出一个想法、实际发生一件事。

| 内容                                       | 权威来源                               | 是否直接推进                   |
| ------------------------------------------ | -------------------------------------- | ------------------------------ |
| 她对当前话题好奇、想继续了解               | 当前段落指导与自然回应                 | 不直接写关系状态               |
| 用户说愿意等、想再见或想靠近               | 完整当前用户发言，加必要的明确意图复核 | 可形成合法事件请求，尚不是结果 |
| 玩家位置、道具公开、已约好再见、已共度一夜 | 作者允许的事件及实际呈现回执           | 才提交相应checkpoint           |

LLM对“这一段似乎聊得够了”的判断至多是导演建议，不能直接设置trust/chemistry、跳到下一章或给自己开权限。涉及必须知晓的关键内容，保留确定性的短锚点，实际呈现后再加入相应已知事实。

段落的转移尽量绑定真正发生的事件：同意共桌、决定一起去走廊、她提出短暂离席后用户选择等候、双方明确另约见面。纯聊天不必产生Ink revision；一段话题可以多聊，也可以有不同表达。

开放交流需要允许提前结束，不能靠封锁告别来保证时长。原先76个固定台词节点不能继续拿来充当76道用户必须回答的题。

## 用补妆前后走一遍

**当前处境**：双方聊过职业之外的自己，刚有一句话需要解释。她还没有离席，玩家还没有答应等。

**可能生成的对白示例**：

> 米拉：“这句我听明白了。给我两分钟整理一下，回来以后，我们别再拿玩笑替自己回答，好不好？”
>
> 心声：“好像终于能把刚才那点紧张放下来一点。别急着假装自己从头到尾都很镇定。”

示例不存成必播台词。推荐根据实际回应生成，可能是：

- “你慢慢整理，我在这里等你。”
- “我还想把刚才那句话解释清楚，先陪我聊一会儿。”
- “我今天得先走了，不过很高兴认识你。”

用户发送后分别解释为等候、继续当前交流、结束今晚；假设或含糊附和则不擅自切镜。

如果选择等候，Ink与播放器安排角色独处镜头，玩家位置不变。切镜失败不记录她已返回；玩家途中结束则冻结已呈现前缀。返回后，LLM只根据真实发生的等候、位置与对话生成承接，不能把作者心声误当成玩家知道的事。

## 公共协议和旧会话

推荐的目标形状为 `{label,draft}`。为避免同一轮同时做大规模协议清理，第一阶段可保留旧interaction字段的兼容读取，但服务端不再产生、客户端不再用它执行推荐。后续删除该字段时，单独协调前后端版本并再生成OpenAPI。

旧缓存中的推荐应丢弃或重新生成，不丢用户草稿与回看。现有3.0逐句存档不能直接套用新的16场状态机；采用新剧情包版本，新会话使用新设计，旧会话明确提示版本不兼容后由用户选择重开，不静默迁移或清空。

## 实施顺序与审阅重点

1. 先改一段普通聊天与补妆前后的小切片，验证推荐确实来自LLM且不被固定句覆盖；保留剩余剧情的可运行状态。
2. 小切片确认后，将第一晚其余场景、第二次见面及关系分支迁移到同一机制；不长期并存两套推荐逻辑。
3. 清理废弃配置、逐句动作和旧协议字段，做完整路线、长聊、转话题、拒绝、中断与恢复验证。

审阅时重点看三项体验决定：普通推荐不再绑定动作；首屏默认只给开场与输入；事件后自然承接可能多一次模型调用。三项会影响操作感和等待时间，不能当成只删除一个JSON字段的小修改。

30分钟仍是完整体验目标，需要靠16场各自有内容、人物有主动性和用户参与来支撑；改为动态生成后，原先预写对白的字数不再能证明实际时长。应验证多种表达和路线，而不是固定76次点击是否能走完。

本轮仅完成设计，不运行功能、运行时、E2E或付费Provider请求，不启停服务。
