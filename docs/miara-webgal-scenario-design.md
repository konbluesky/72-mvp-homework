# Miara + WebGAL：八场景叙事互动方案

日期：2026-10-31（Asia/Shanghai）。版本：**v0.2，多背景与故事扩展**。状态：**设计基线，实施范围另行记录**。

本稿的待实施描述对应设计时点；八背景和互动链已开始落地，当前实现与验证边界见[八场景实施记录](acceptance/miara-webgal-story.md)。

本稿综合已读取的“设计 WebGAL 互动场景”“开始落地 WebGAL 接入方案”两个聊天、[实施 prompt](prompts/miara-webgal-implementation.md)、本地原始需求第 1–3 页及当前工作区源码。聊天中的历史验证只作为历史背景，当前进度以代码为准。保留其他会话的未提交修改。

用户最新入口约束：原版 Vue/Haru 与 WebGAL 两页长期并存。保留原版语音、显示与回看交互；完成新页不意味着删除原版或自动替换首页。2026-11-01 用户调整：两页均默认 Haru，WebGAL 保留 Miara 显式可选。

## 1. 方案结论

首个完整体验改为 **《雨停之前：最后一盏灯》**：一家即将结束最后一晚营业的咖啡馆里，米拉仍在等一位旧友。玩家从避雨的过客成为同行者，经过店门、大堂、座位、走廊和结账台，逐步发现“失约”背后的留言，并和她决定今晚如何结束。Haru 为默认渲染模型，Miara 保留并可显式切换。

每个主要互动形成一条连续因果链：**玩家意图 → 可验证的剧情事件 → 地点与环境变化 → 角色回应 → 后续选择**。人物动作承担表演；地点转换、道具状态、营业灯与雨夜街景承担场景变化，两类目标分别验收。

本版设计 **8 个独立背景地点、三幕主线、三种结局**，替代上一版仅有三个机位视图的范围。正常探索约 10–15 分钟，允许自由聊天延长；保留一条能在 3–5 分钟展示核心能力的精简路线。至少五个真实背景是硬门槛，目标交付下文全部八个背景；照片特写、同图裁切、雨势或亮度变体不计入八个背景。耐玩性来自线索顺序、谈话选择、回访反馈和结局差异，不新增第二套剧情后端。

| 当前对话触发明显视觉事件 | 请求照片触发照片呈现；请求阅读留言触发信件；决定离店后翻牌、熄招牌并切到街道     | 由当前选择与已确认节点触发，不能按开场计时自动播放         |

原题中的琥珀雨衣、星星发夹是可选故事种子，不强制把 Miara 改造成该外观。业务 `character: 'mira'` 与渲染 `modelId: 'miara' | 'haru'` 分离；角色选择器展示样例名称与归属。服务端人设保留成年身份与摄影/等候背景，将不匹配模型的外形文字移出通用 prompt，避免角色自述与画面冲突。不给官方样例自行认定年龄或原创归属。

## 4. 八个背景与三幕故事

### 4.1 故事核心与固定设定

**故事问题：咖啡馆即将熄掉最后一盏灯，她还要继续等一个没有出现的人吗？**

基调为雨夜、轻悬念与温暖陪伴。剧情有起因、发现、转折和行动结果；不靠随机事故或强行反转制造故事性。以下设定是待实施的故事文本，不代表当前后端已经支持：

- 咖啡馆名为“雨停之前”。今晚是旧店最后一晚营业，之后搬迁；大堂已收起部分桌椅和照片。闭店由剧情节点推进，没有现实时间倒计时。
- 米拉是一名成年旅行摄影师。她与成年旧友阿岚曾一起旅行并办过小型摄影展，后来渐渐失去联系。她带着一张海岸照片，回到曾经约定重逢的地方。
- 她以为阿岚没有赴约。事实上，阿岚下午来过，因为行程无法留到晚上，在结账台留下署名给米拉的信。信里邀请她把自己的作品带去下一站的展览；没有承诺阿岚此刻正在街外等她。
- 米拉真正犹豫的，是如何重新开始联系，以及是否愿意不再让等待决定自己的行程。玩家可以陪她了解留言，也可以选择不追问。
- 阿岚通过固定文字道具与回忆被提及，首版不增加第二个可对话模型。信件内容、人物关系和过去事件由场景设定固定，LLM 不临时改写真相。

留言正文建议固定为：

> 米拉，我下午来过，没能等到晚上。下一站的展览，我给你的照片留了一面墙。不是让你追上我，是想知道你现在拍下了什么。如果你愿意，我们重新联系。——阿岚

玩家不需要扮演侦探完成全部搜集，也不能凭读过一封信就宣布两人已经和好。高潮是米拉作出今晚的选择，并在场景中实际行动。

### 4.2 八张独立背景清单

全部 ID 是拟议的本地资源注册项，**新增图尚未制作**。每个背景需要独立文件与构图，不能用同一张图缩放冒充多个地点。

| 编号 / 背景 ID       | 背景与画面重点                                             | 剧情用途与可交互物                                           | Miara 的在场方式                                   | 明显的场景变化                                                   |
| -------------------- | ---------------------------------------------------------- | ------------------------------------------------------------ | -------------------------------------------------- | ---------------------------------------------------------------- |
| S01 `street-wide`    | 街角咖啡馆远景：完整店体、楼上暗窗、雨中斑马线与一盏暖招牌 | 开场建立空间；选择进店或观察停业告示                         | 开场可暂不在画面，进店后相遇                       | 从冷色街景进入暖色店面；告别后可回望熄灯的店                     |
| S02 `cafe-front`     | 门头近景与雨棚：玻璃门、门铃、营业牌、滴水檐口             | 阅读“旧店最后营业日”；进门、出门、翻转营业牌                 | 相遇后同行；门边侧身/回看，用剪辑衔接              | 营业牌翻为休息、室内灯逐区关闭，屋檐水滴仍在                     |

| S06 `washroom`       | 卫生间公共洗手区：镜面、洗手台、暖色壁灯与门外走廊光       | 可选的情绪缓冲：整理被雨淋湿的随身物，谈她为何一直没开口联系 | 与玩家停在公共洗手区；不需要私人隔间或复杂洗漱动作 | 水龙头/滴水与镜面光线形成独立气氛，整理后湿手帕成为可见物        |
| S07 `counter`        | 吧台结账台：收银机、托盘、写有“米拉”的信封、搬迁地址卡     | 发现并请求阅读留言；决定是否留下回信或结账                   | 先注意到名字，再关注信；后期可留下回信             | 信封到信纸、回信放入托盘、付款状态或收据出现                     |
| S08 `street-walk`    | 店外街道近景：路灯、湿路面、街角方向牌，回望可见同一家店   | 主动出发或温柔告别的结尾，继续谈下一步                       | 选择同行时与玩家在街边；其他结局按实际去向处理     | 雨势逐渐变轻、招牌暗下、路面反光改变；人物与店门形成新的空间关系 |

S01 是看见整家店的街角远景，S08 是离店后沿街前行的近景，视点、道路构成与用途不同；S02 是门头与门槛。三者不能共用同图裁切凑数。照片和信件特写是额外道具视图，也不占八个背景名额。

### 4.3 地图与可达关系

入口路线：**S01 街角远景 → S02 门头 → S03 大堂**。遇到米拉后，大堂连接 **S04 座位、S05 照片墙、S07 结账台**；照片墙走廊连接 **S06 洗手区**。离店从大堂经门头通向 **S08 街道**，可回望 S01。

允许通过“去吧台看看”“想回座位”“我们出去吧”等自然语言提出移动，也提供可发现的地点入口。已访问地点可用简洁地图快捷返回：后端校验可达路线，执行必要的短转场，不强制玩家重复逐扇门点击。

开场提供“走进店里”和“直接开始交谈”的入口；后者以受控转场略过外景介绍，不伪造玩家已经阅读了告示。地图不是任意场景相册，未读信件或未作出的决定不会因换背景自动获得。

### 4.4 三幕推进与场景事件

章节由已确认的叙事节点推导，顺序允许局部变化；不按“第几轮”或“进页面多少秒”触发。

| 幕 / 核心问题                        | 主要地点与事件                                                             | 玩家可以做的选择                                   | 角色与环境的共同回应                                                                        |
| ------------------------------------ | -------------------------------------------------------------------------- | -------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| 第一幕：最后一晚，她在等谁？         | S01–S04；发现搬迁告示，在打包中的大堂遇见米拉，窗边有一个空位              | 坐下聊、先看店内、问等候的人，或只说自己来避雨     | 门铃与雨声进入室内声场；她从戒备转为愿意交流；旧店即将结束的线索始终可见                    |
| 第二幕：没有出现，是否等于没有来过？ | S05 可见联展海报；S07 有署名给她的信；S04 可分享海岸照片；S06 可谈她的犹豫 | 先聊回忆再看信、直接去吧台、跳过照片，或暂不打开信 | 海报/信纸进入舞台前景；同一地点回访时道具状态与台词改变；她对“失约”的理解可能转变           |
| 第三幕：灯灭之前，我们去哪里？       | 已呈现信件或完成一段不追问的陪伴后，米拉愿意讨论今晚的安排                 | 出去走走、留下回信后离开、继续再坐一杯             | 经合法决定触发回信/结账、门牌翻面、灯光收束与对应结尾地点，不用统一弹一个结局文字框代替演出 |

**转折场景示例：** 在结账台点到写有她名字的信封，米拉先认出笔迹，说“我以为，她已经不记得这里了”。玩家可以说“要打开看看吗”，也可以说“不急，先回去坐一会儿”。只有信纸真正打开并呈现正文后，后续台词才允许引用阿岚下午来过和展览邀请；信封外观只能证明这里有一封署名给她的信。

**情绪缓冲示例：** 在公共洗手区，米拉整理湿手帕，玩家说“你也可以先想清楚自己想去哪儿”。她可以承认“我带了照片，却一直没想好第一句话”。这段不提供必须搜集的钥匙或隐藏密码，作用是让她的最后决定获得人物动机。

**行动高潮示例：** 玩家提议“先把回信留下，我们出去走走”，她说“好。这次我想自己选下一站”。回信进入托盘并确认后，她与玩家经过门头，营业牌翻面，街道背景就绪，雨势缓和，最后镜头回望逐渐暗下的招牌。每一步都有可取消的执行与独立事实边界。

### 4.5 三种结局与条件

结局由明确选择和已确认的内容决定，不用隐藏好感度、点击总次数或随机数判定。结局后可继续聊或选择开始新故事，不偷偷清空本次记忆。

| 结局                  | 触发与内容                                    | 最终地点及场景结果                                     | 不同信息下的差异                                                                     |
| --------------------- | --------------------------------------------- | ------------------------------------------------------ | ------------------------------------------------------------------------------------ |
| A《下一站，由我决定》 | 玩家提议离开，她同意主动出发                  | S07 可结账，S02 翻牌，S08 并肩走到路灯下，回望旧店灯暗 | 读过信可谈展览邀请；没读信则只谈自己的下一段旅程，不能凭空引用邀请                   |
| B《给未说出口的话》   | 她决定留一张回信/联系卡，玩家尊重不再继续追问 | S07 留下可见回信，S02 门前告别，S01 回望旧店           | 信未读时是主动留下联系的卡片；已读时可回应信中内容。没有真实展示的回信不能记为已留下 |
| C《再坐一杯》         | 玩家选择留下，她也愿意暂时继续等              | S04 保留一盏桌灯，其他区域收灯，雨仍可继续             | 已知留言时讨论自己想如何答复；未读时安静陪伴，不伪造释怀或秘密揭晓                   |

三种结局没有道德评分。拒绝照片、暂不读信、先谈自己的经历，都可以抵达有意义的收束；不把“把所有道具点一遍”作为完成故事的条件。

### 4.6 耐玩机制与节奏

- **线索顺序改变回应。** 先看海报再读信，她会认出共同经历；先读信再回看海报，会谈到给作品留出的那面墙。两种顺序不改写信的正文和朋友关系。
- **回访有变化。** 看过的海报用简短反应；读过的信可以重读，回信放下后托盘多出物件；回到座位时她不再重复首次介绍。离店后回望店面使用熄灯变体。
- **选择影响行动。** 继续陪伴保留座位与桌灯；离开进入门头和街道；留下回信改变结账台。不是只把同一段台词替换几个词。
- **自由聊天参与剧情。** “我也在等人”可以转向共同经历，“不想看照片”走陪伴路线，“去吧台看看”进入探索。模型在允许节点内组织表达，不能替玩家作出离店、读信或留信的决定。
- **动效服务地点。** 门铃、檐滴、雨窗、走廊光、纸张展开、营业牌和熄灯有不同声画主题；三种新人物动作保留为表演基础，场景变化另行实现与计数。
- **避免消耗式重复。** 同一活动热区合并重复输入；已读道具本地重开不强制新模型请求；导航可复用确定性场景节点，重要谈话仍走既有 LangGraph。

建议完整体验约 10–15 分钟；精简演示可走 **S01 → S02 → S03 → S04 → S07 → S08**，保留交谈、一次线索展开、一次打断、离店与恢复失败，覆盖六个不同背景。S05/S06 是可选但完整制作的支线地点，不是为了完成地图必须经过的任务点。

### 4.7 图像依据与天气规则的明确修订

当前 `travel-photo.svg` 是明亮天空、海面、海岸与浪花，**没有人物**。可以成为共同旅行的风景记录，不能称为人物合照；联展署名由新海报提供，留言真相由新信件提供，不能让模型从旧风景图里编出人物或文字。

服务端场景上下文应包含可信的素材语义、固定故事真相、玩家/米拉当前已知的信息和本地点可用意图。未呈现的信息不进入“玩家已知”，模型读取的作者设定也不能提前泄露给玩家。无须为固定素材另加付费视觉识别。

**本版正式调整旧的天气前置建议：离店结局中的雨势缓和，由米拉已同意离开、且门头/街道已经实际呈现的节点触发；与是否看过照片分别判断。** 不看照片也可以走到街道结尾。继续坐一杯的分支可以保留原雨势。

当前代码仍硬编码照片前置。实施新故事时必须同步修改 `scenario/rules.ts`、Graph 的照片等待/环境筛选、SessionManager 的回执依赖、Scheduler 的照片阻塞策略、Mock、fixtures 与相关测试源码；不能只修改 prompt。环境依旧只在实际可见的雨窗/室外变化成功后提交独立回执，不把选择离开或换地点当成已经看见雨变小。

## 5. 深度融合：一套舞台与连续的空间

### 5.1 八张背景的美术约束

先确定同一家店的平面关系和公共元素，再制作各地点独立背景。统一门头“雨停之前”、深木色窗框、暖黄壁灯、海绿色座椅与摄影展视觉；室外保持同一雨夜，不突然变成白天或另一家店。

门头画面中门在左、主雨窗在右；大堂后侧连接吧台，侧面走廊通向照片墙和洗手区。反打镜头允许左右关系随视点改变，但门、窗、吧台的实际空间关系不变。Miara 在不同背景中的大小、朝向、脚下/桌沿遮挡各有本地布局 profile，不能八张图都把同一个半身模型粘在画面中央。

每张背景交付：独立基础图、可拆的必要前景/道具、热区与人物锚点、雨/灯/门等效果区域、可返回出口。招牌熄灯、信纸展开、小雨等属于状态变体，另列清单；最低五张背景及目标八张背景按基础图验收。

### 5.2 同一引擎执行全部地点

背景、角色、可见道具与场景动效挂入同一 WebGAL 管理舞台，使用同一 Application、Pixi 依赖、坐标变换和更新节奏。室内常用层级为窗外景与雨 → 窗框/室内 → Miara → 桌沿/吧台前景 → 道具特写；街道则有远景建筑 → 世界雨层 → 角色与雨棚 → 近景水滴/反光。

- 背景继续经 `StageStateManager → syncPixiStageState` 执行；角色复用固定 Cubism4 入口与 WebGAL figure 容器。driver 只在受控更新钩子中混合参数，不创建第二个 canvas 或独立 ticker。
- 当前 SVG 仅能作为其中一个背景的素材来源。拆出重复的桌沿、杯子和纸张，不用旧图裁切八遍代替新背景；新地点所需图片应真实制作并登记来源。
- 室内原生雨效果使用窗区域遮罩；室外使用有深度和雨棚遮挡的世界雨层。原生 rain 的前/背景容器需经受控适配，不能原样全屏覆盖所有室内人物。mask、镜头和热点共享布局变换。
- 地点切换、同地点镜头、天气、道具公开分别建模：走到吧台是地点转换，座位内看窗是机位变化，翻信纸是道具事件。三种人物动作不计作地点变化。
- 场景动效包括可见门开启、营业牌翻面、灯分区收束、信纸展开、回信进入托盘、街道雨势与反光变化。每种动效都有与剧情相关的触发节点和可取消句柄；不是开场自动循环演示。
- React 只保留输入、字幕、错误、无障碍热区、地图和历史入口；主要画面由舞台执行。DOM 热区投影同一舞台目标，不拥有第二套道具动画或剧情状态。
- 手机端按各背景的安全构图区裁切；地图入口、返回、录音与打断可达。软键盘、旋转后用实际舞台变换重新定位热区，不让门口热点残留在下一张背景。

### 5.3 人物在场与场景声音

开场外景可以无人；大堂相遇后默认由米拉同行。她在座位、走廊、吧台与门口使用不同站位/裁切，必要时用空镜衔接，不承诺当前模型尚未具备的完整走路和坐站动画。她不在场时不继续对空画面播近距离人物语音；纯外景说明用清楚标注的受控场景字幕。

门口可听檐滴/门铃，室内雨声压低，洗手区有不同混响，街道恢复开放声场。音效与环境声仍由 Scheduler 所持有的统一音频端口治理，地点变化后旧声场退出；禁止原生剧情音轨与现有播放器同时推进。

Miara 服装/羽翼保持样例造型，用合理构图、遮挡与有限色调调整协调场景。正式原创视觉资产仍独立交付，不靠灯光处理宣称已经更换服装或人物设定。

## 6. Miara 资产中必须先处理的问题

静态检查发现：三个原始 motion 的 `Meta.Loop` 都是 `true`，并包含嘴部、人物、精灵、水面和全局位置等多类曲线。CDI 还列出 `PartBackgroundAll`、`PartBackground`、`PartWaterSurface*`、`PartSparkle`、`PartFairy*` 等部件。这些内容会直接影响场景融合。

1. **先做模型通道与部件清点。** 在受控加载阶段读取真实参数数量、ID、min/max/default 与部件索引；CDI 和 motion ID 只能证明候选名称，不能证明 `.moc3` 的实际范围、父子关系或自然形变。未知 ID 不能使用 wrapper 虚构的索引。
2. **分离模型自带舞台内容。** 核实水面、背景、反光/闪光部件的依赖后，在咖啡馆 profile 中关闭不适用的样例景物；原始文件保持原始字节。若不能安全关闭，记录具体部件和可见问题，再选择透明导出或补资产，不能用遮罩把缺口假装解决。
3. **精灵与人物分别归属。** 默认不把精灵翅膀或水面运动当作 Miara 的身体动作；若保留精灵，作为受控装饰说明，首版不增加第二个会说话或拥有剧情事实的角色。咖啡馆 profile 的部件约束必须防止原始 motion 再次打开不适用的景物。
4. **原始动作只供显式样例预览。** 保留 `Idle/Scene1`、`Tap/Scene2`、`Flic/Scene3`。原始预览有停止和有界时长，退出恢复当前姿态；生产对话关闭自动 Idle、随机 Tap 与样例音轨，不自动循环全通道动画。
5. **为两种模型分别绑定能力。** 不复制 Haru 的整组必填参数或绝对角度到 Miara；例如 Haru 所用参数并非全部出现在 Miara CDI。缺少某候选通道时选择已验证的替代方案或报告能力不足。

只有运行时文件，没有 `.cmo3/.can3` 不妨碍已有绑定内的新参数动作，但不保证坐站、侧身、抓握或口型的最终表现。当前 `Groups.Ids` 与 `HitAreas` 为空，需要显式验证嘴眼和本地交互命中，不能依赖 SDK 自动推断。

## 7. 人物动作与场景编排分别落实

以下名称是本地行为草案，**不是已经存在的动作资产**。时间为调试起点，实际幅度必须在真实范围和画面中校准。

| 新行为                      | 演出过程                                               | 候选通道与占用范围                                   | 用途/退出                                                     |
| --------------------------- | ------------------------------------------------------ | ---------------------------------------------------- | ------------------------------------------------------------- |
| 抬手示意 acknowledge        | 看回玩家 → 单侧前臂小幅抬起 → 短暂停留 → 放下，约 1 秒 | 一侧 `ParamArm*`、必要手指与轻微头部，避免全身升降   | 首次招呼或叫她；新输入立即释放，恢复当前倾听/思考姿态         |
| 偏头沉思 ponder             | 眼神稍移 → 偏头与眉眼调整 → 保持 → 回看，约 1–2 秒     | `ParamAngle*`、`ParamEyeBall*`、眉眼；不绑定嘴部开合 | thinking 的非说话动作；等待很长时保持安静姿态，不循环夸张思考 |
| 望窗再回看 lookWindowReturn | 眼球先行 → 头/上身跟随 → 望窗保持 → 回看玩家，约 2 秒  | 头部/眼球/小幅身体通道，与窗户锚点方向一致           | `lookWindow` 的新实现；镜头可在转头后启动，新输入优先回到玩家 |
| 关注照片 photoFocus         | 视线下移 → 微倾头 → 有能力时小幅示意 → 看回玩家        | 头/眼球及已验证手臂，不以整张图位移冒充递手          | 与独立照片事件组合；不要求编造握纸/递手 motion                |

三种必做新行为应有独立曲线定义或新动作文件，以及进入、保持、退出、取消的代码归属。不是给 Scene1–3 起三个中文名；验收应在原始 motion 禁用时仍能分别触发。

参数混合按通道分工，而非最后一帧全量覆写：

- 生命周期失效与闭嘴约束优先；新输入的合法基础状态高于旧句手势。当前合法句动作可以占用自己的头/手通道，结束后平滑交还当前基础姿态。
- `afterMotionUpdate` 等已核实钩子合成人物头、身体、视线与手臂，供后续物理消费；头发/衣袖等物理输出保持物理归属，避免每帧归零。
- 情绪控制眉眼与嘴角形状；眨眼在已验证眼睑通道混合，不能把思考的眼睑表达覆盖掉。
- 嘴部最终开合只用 Scheduler 当前实际音频包络；未播放、字幕模式、失败、取消时为零。原始 motion 的嘴部曲线必须屏蔽或在最终约束中覆盖，不能“动画会张嘴”冒充语音口型。
- pointer focus、自动 breath/blink 与手动驱动各自只能保留一个来源。降动态模式保留关键静态姿态、情绪与真实口型，减少摇摆、粒子和镜头移动。

坐下、起立、托腮、端杯逐项评估已有手臂、手指、腿部绑定；有手指参数也不证明能自然握杯。座位采用桌后构图，门口/大堂采用站立构图，跨地点用短空镜、淡入淡出与受控脚步音衔接，不以整张模型平移宣称完整行走。

人物动作之外，至少完成以下场景编排，分别记录实际背景与对象变化：

| 场景编排         | 动作与画面顺序                                                             | 完成依据                                                   |
| ---------------- | -------------------------------------------------------------------------- | ---------------------------------------------------------- |
| 雨中进店         | S01 街角 → S02 门头，点击进门 → 门/门铃 → S03 大堂；米拉在已声明的位置出现 | 新地点背景、人物、出口与声场实际就绪；不是她抬手就算已进店 |
| 到吧台读信       | S04/S03 → S07；她关注姓名 → 用户请求打开 → 信纸进入前景                    | 地点和信件分别呈现，信封成功不能替代正文成功               |
| 公共洗手区停留   | S05 → S06，灯光/滴水声切换，她整理随身物并谈犹豫                           | 背景与可见物变化；不要求用未知参数表演完整洗脸动作         |
| 留下回信         | 用户明确选择、她回应 → 回信进入 S07 托盘 → 可再次查看                      | 道具最终位置实际可见后，才记录已留信                       |
| 离店与最后一盏灯 | 她同意离开 → S02 翻牌 → S08 街道 → 窗内灯/招牌收束、雨势缓和               | 地点、灯/营业牌、天气各自完成；被打断时保留已成功的部分    |

## 8. 多地点故事的状态、协议与调度

### 8.1 复用单轮链路，注入故事定义

继续使用 `begin → input → LangGraph → 受控事件 → PlaybackScheduler → Bridge → 引擎 → receipt → SessionManager`。对话回复沿用 audio.ready；结构化导航、读道具与故事选择也归属同一轮次机制，不在热区 handler 里直接改地点、播放声音或提交剧情。

服务端 `ScenarioDefinition` 组织固定真相、地点图、允许意图、线索内容、选择前置和事实归并。Graph 注入该定义；SessionManager 先验证身份、已下发目标、冻结集合与去重，再交给场景策略处理。前端 `SceneDefinition` 提供八个背景及变体、锚点、人物站位、转场、资源白名单和实际呈现条件。

为纯导航增加 LangGraph 内的确定性分支，按当前地点与许可返回场景事件，无需每次点门都请求 LLM/TTS。需要人物回应、理解自然语言或作出剧情选择时继续规划；关键真相、地点边和结局条件不交给模型自由生成。保留既有 ProviderSet、连接监测、录音草稿、队列与取消机制。

### 8.2 区分地点、机位、道具、知识与选择

| 状态           | 本版定义                                                      | 如何形成                                                              |
| -------------- | ------------------------------------------------------------- | --------------------------------------------------------------------- |
| scenario       | 固定故事 `cafe-last-light`                                    | 可信组合入口选定，不由模型换剧本                                      |
| location       | 上述八个 locationId 之一                                      | 合法 location 事件实际呈现后更新；目的地只是 requested 时不能当已到达 |
| shot / view    | 当前地点内的看窗、人物近景等本地机位；照片/信件有专用道具近景 | 受控机位 cue 或道具事件，不增加背景地点计数                           |
| revealed props | 已公开的照片、已读的停业告示/联展海报/留言                    | 各自成功呈现；到过吧台不等于读过信                                    |
| choices        | 用户明确提出、服务端验证的离开/留信/继续坐等选择              | 接受输入表示选择成立，相关行动仍需呈现；不能直接写已出店/已留信       |
| ending         | 已完成的三种结局之一，可空                                    | 所需选择、角色决定台词和相关地点/道具/灯光的合法回执齐备后提交        |
| weather        | 原 rain / rain-soft 仍作为全局雨夜状态                        | 按第 4.7 节新规则，变化实际呈现后确认                                 |

章节点从已确认内容和选择推导。场景上下文传入当前地点、在场角色、允许意图、已知线索、已作选择与可用事件，不传浏览器资源 URL。作者真相与玩家已知信息分别标注，约束角色不能在信件失败或尚未打开时泄露正文。

不为探索增加隐藏好感度。`visitedLocations` 如需保留，只是有界的已到达地点集合，不作为凑访问次数的结局门槛。纯地点移动不必生成一条虚构“用户说话”的历史；应以可信场景观察摘要供后续规划承接。

### 8.3 必须补齐的严格契约

以下均为拟议变化，当前协议仅有照片/环境事件。实现从 `packages/protocol/src/index.ts` 开始，同步服务端、客户端、Mock 和 OpenAPI：

| 增量                     | 形状/白名单建议                                                                                                      | 关键约束                                                                                               |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| interaction input        | 严格区分 `move`（八个 locationId）、`inspect`（告示/海报/信封等语义目标）、`choose`（三种故事选择）、现有聊天/看照片 | 保留 generation/inputId；当前地点、可达边、是否在场和剧情前置由服务端校验；模型不生成路径或任意对象 ID |
| location event / receipt | `type: location`，固定 locationId；回执新增 `kind: location`                                                         | 从位置、目的地、转场与人物布局均由注册表决定；成功后才更新当前地点                                     |
| prop event / receipt     | 新告示、海报、信件正文、回信使用严格道具枚举；原照片继续独立 photo 事件                                              | 信封/正文/回信不是同一事实；读信、留信需明确意图和分别呈现                                             |
| ambience event / receipt | 营业牌、最后一盏灯、招牌熄灭等受限状态                                                                               | 场景已到达、对象实际变化才成功；不以普通 location 或动作回执代替                                       |
| 无语音事件下发           | 增加严格 `presentation.ready` SSE，用于纯导航、固定道具或受控场景演出                                                | 不能塞进假 audio.ready 或伪造音频 URL；Scheduler 加入同一有序队列/预算，issued target 必须可登记与回执 |
| 会话快照                 | 加入严格 location、线索公开状态、有界选择与 ending 投影；保留独立天气/照片事实                                       | 恢复到已确认地点及道具状态，不重演历史；机位可恢复为该地点中性机位                                     |

现有 `reply.done.segmentCount` 已允许 0，但这不代表无音频场景管线已经实现：当前事件依附 audio.ready，SessionManager.issue 也依赖音频 payload。需一起补纯呈现目标登记、队列 drain、生成结束与所有呈现结束的区分，不能发一个 segmentCount=0 就立即宣称转场完成。

全部事件仍由服务端生成 eventId。客户端提交回执时不能直接携带任意剧情事实。输入幂等摘要包括结构化意图和目标；同一 inputId 换目标必须冲突。对话中的“我们去吧台”映射到语义请求，前端不解析模型生成的 WebGAL 脚本。

跨轮可覆盖状态按服务端已下发 generation/片段/事件顺序应用，必要时补充场景语义版本。晚到旧冻结回执可以补全合法的已读线索，但不能把当前位置、灯光或结局倒退到新事件之前。纯机位预览不写当前地点。

新增事件、回执类型和快照字段需要协调 schema 版本与部署，不假设旧 v1 严格客户端仍兼容。不得用任意 string/record 替代场景枚举，也不让 LLM 调用 parser/runScript 执行任意剧本。

### 8.4 地点事务与剧情呈现顺序

一次跨地点动作以“校验 → 预加载 → 可取消过渡 → 提交目标背景/人物/出口/声场 → 实际呈现 → 回执”执行。只在目标就绪后切换；失败或取消时保留最后确认的合法地点与道具状态。

- 移动本身不应被声音故障阻塞；纯导航可无语音完成。人物决定、叙事说明与重要台词仍按原音频/字幕显式确认机制呈现。
- 站位、背景、目标热区和人物在场是一组地点事务；不能背景换到街道而热区、台词和人物仍是座位状态。短空镜可以暂时无人物，但须明确是过渡而不是加载成功。
- 同一地点内：她先关注信封，用户请求打开，信纸正文呈现，才允许台词引用信的真相；未听完的决定台词不能冒充已经完成的角色决定。
- 环境和道具分别返回 presented/failed；页面隐藏、对象透明/遮挡/视野外、上下文丢失时不能确认。commit、Promise resolve 或单次 rAF 不足以证明可见。
- 结局是多项实际结果的组合。离店地点已成功、信件未成功时，只能保留已到街道，不能写已读信或已留信；取消也不能一键回滚用户已经看到的合法事实。
- 动作、转场与声音锚点由 Scheduler 的本地 cue/执行句柄管理；前奏短而有界，音频真开播才 speaking，声音结束后视觉仍可在预算内收束。

## 9. 导航、预览与剧情行为的边界

| 操作                                | 是否需要 planner                                         | 状态/回执边界                                                |
| ----------------------------------- | -------------------------------------------------------- | ------------------------------------------------------------ |
| 点已开放出口或返回已访问地点        | 可走 Graph 内确定性导航，无需 LLM                        | 使用真实 location 事件和回执；不强制写假聊天消息             |
| “去吧台看看”“想离开这里”等自然语言  | 同一轮规划/受限意图解析                                  | 映射合法地点与选择，不能自动跨越未知前置                     |
| 初次请求照片、读留言、留下回信      | 按场景节点规划或确定性呈现；角色回应仍可使用既有 planner | 意图许可与各自 photo/prop 结果独立                           |
| 重读已公开照片/信件、关闭特写       | 无需新增模型请求                                         | 本地浏览，不重记首次事实；关闭后回当前地点，不统一跳座位     |
| 开发面板任意背景、雨势、原始 motion | 否                                                       | 独立预览 owner，不写剧情位置、线索和结局；退出恢复已确认状态 |
| 切换 Miara/Haru                     | 否                                                       | 模型更换保留地点、已知内容和剧情选择，显式进行               |

开发预览与业务演出互斥，统一经过宿主受控端口，不另起播放器。产品地图按合法路径导航，资源预览相册放开发面板，不能共用一个按钮让“看图”和“人物走到那里”含义混淆。语音入口继续服从服务端 capabilities.voiceInput。

## 10. 生命周期、失败与切换

所有执行同时核对 TurnIdentity、stage lease/epoch、场景 revision、角色实例 lease；跨地点事务还带请求位置与目标版本。预览 owner 不具有业务事实权限。

| 情况                           | 当下处理                                                           | 必须保留的边界                                                                  |
| ------------------------------ | ------------------------------------------------------------------ | ------------------------------------------------------------------------------- |
| 录音/新文字/另一个有效地点意图 | 同步停声、闭嘴、失效旧 cue、冻结已呈现回执，再走新轮               | 旧 finally、转场结束、图片解码不清理或覆盖新轮                                  |
| 跨地点加载中打断               | 丢弃未提交目标，保留最后合法地点；最新意图重新校验路线             | 未见的新背景不计入到访，不说已经走到那里                                        |
| 新地点已呈现、道具未呈现       | 保留新位置，撤销临时道具                                           | 到过结账台不等于已经读信；回旧地点也不抹去合法已读线索                          |
| 照片/信件展开失败              | 明确对应素材失败，可再次请求或继续其他话题                         | 未读信不能泄露正文；照片失败不阻断独立的陪伴/离店路径                           |
| 留信/翻牌/熄灯中途取消         | 冻结已成功的各项结果，取消尚未成功的项                             | 只完成到街道不能宣称整套结局完成，也不能清除已放下的回信                        |
| 环境已经变化后打断             | 保留全局小雨状态，各地点按自己的雨窗/室外效果投影                  | 旧轮取消不能删除持续天气 scope，室内不得因此开始全屏下雨                        |
| 快速切地点/机位                | 只允许最后有效 revision 挂载；资源就绪后提交，失败保留合法旧画面   | 旧回滚不能覆盖新地点；旧热区、声场和人物站位不得残留                            |
| 切 Miara/Haru                  | 统一打断、冻结当前轮，失效旧角色 lease；新模型/参数/首帧就绪后完成 | Haru 全部模型、poster、归属与实现保留；地点、线索与选择保留，旧加载只释放旧实例 |
| Miara 加载失败                 | 明确失败、重试、允许显式选择 Haru；可保留已就绪原角色              | 不静默换 Haru，不用 Haru poster 冒充 Miara                                      |
| 音频不可用                     | 显式恢复或选择字幕；嘴闭合；独立纯导航可继续                       | 文字确认不冒充声音完成，不启动第二套原生配音                                    |
| 断线/重建/切后台/上下文丢失    | 取消活动 scope；同步待确认回执后取快照                             | 恢复最后确认地点、道具、灯光、天气与故事选择；不默认跳回座位，不重播旧内容      |

切角色失败时可以保留用户此前明确选择且仍可用的旧角色，并说明切换未成功；首次默认 Haru 失败则等待重试或显式选择 Miara。结局 A/B 的离店动作必须已被选择，不能让恢复或回执重传自动作出离店决定。

## 11. 背景、道具与 Mock 交付

### 11.1 真实资源清单

需要新制作/整理的素材包括八张基础背景，以及停业告示、联展海报、署名信封、信件正文、回信/联系卡、营业牌和必要灯光遮罩。每项登记本地资源 ID、实际路径、来源/许可、画面内容与可交互区域。信件/告示的汉字用清晰排版叠层呈现，不依赖背景图中难以辨认的烘焙小字。

既有 café SVG 和海岸图可复用在相应地点，不能充当其余七张图。先制作同一店铺的空间/风格参考，再按第 4.2 节逐张制作与对照，检查店名、门窗、家具、雨向和光线连续性；所有新增背景当前均为待制作，不把设计表等同于资产完成。

建议先完成 S03/S04/S07 的开发切片以打通聊天、读信和导航，随后补全 S01/S02/S05/S06/S08。切片用于开发，不满足至少五背景的最终门槛，也不能宣布八场景交付。

门铃、纸张、脚步、檐滴与雨声均需本地文件和来源；无可用声音时可以明确暂缺该音效，不能引入秘密远程请求。灯牌、信封、信纸和回信状态使用真实舞台对象或可见资源变体，不能只改状态标签。

### 11.2 Mock 与 Live 保持同一故事规则

Mock 通过真实 API/Graph/调度/回执覆盖八地点导航、海报/信件、照片请求/拒绝、离店/留信/继续陪伴三结局，以及打断恢复。纯导航不必合成一句多余台词；重要故事节点使用固定、语义匹配的离线台词与音频。

当前 MockTts 只为 MOCK_LINES 完全匹配文本读取 WAV。新增剧情不能只写新台词而没有音频，需通过既有离线素材流程补齐固定 WAV 与 manifest；旁白可明确采用场景字幕。不得调用 Live TTS 作为 Mock 隐形后备。

Live 保留 Deepgram STT + GPT/LangGraph + Deepgram TTS。LLM 读取相同固定真相、地点与已知线索；没有新素材/没读到信时不能即兴生成“已经呈现”的细节。音效与环境声归 Scheduler 持有的统一音频端口，不让原生 perform 另起失控音源。

新编 motion/profile 与上游模型分开记录，更新适用资产清单、来源和哈希。用户录音、私有图片、密钥与供应商临时 URL 不进入素材目录。

## 12. 实施顺序与阶段交付

| 顺序                 | 具体交付                                                                | 阶段完成条件                                                                       |
| -------------------- | ----------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| 1 · 故事与美术基准   | 固定真相、八地点地图、三结局、背景构图/道具清单与内容说明               | 从进店到收束有可解释路径，八背景不是裁切或换雨势凑数                               |
| 2 · 角色可用性       | Miara/Haru 注册表、真实参数/部件审计、单运行时 driver、三种新动作与四态 | Miara 可用、Haru 显式可选；原始样例禁用仍有新行为                                  |
| 3 · 同页闭环         | Headless 状态、React 输入/字幕/录音草稿、API/连接恢复、Bridge           | WebGAL 同页聊天、打断后下一轮正常；此前不接管默认产品入口                          |
| 4 · 多地点切片       | S03/S04/S07，location/prop/ambience 契约、纯导航事件、读信前后上下文    | 地点、人物、热区/声场一致；未读信不泄露，独立回执可冻结                            |
| 5 · 八背景与完整剧情 | 补齐另外五背景、支线、回访状态、营业牌/熄灯、三结局                     | 全八背景可达；拒绝照片仍可推进；结局改变地点/道具/灯光                             |
| 6 · 交付收口         | 手机布局、失败恢复、资产来源、入口切换、实际验收资料                    | 满足至少五背景硬门槛和八背景目标，按实际范围验收；完整链完成后仍保留两页与可见切换 |

工程面板可以展示位置、已公开线索、事件回执与 owner；产品默认展示场景、可用出口/地图、输入和必要反馈。场景选择、轮次和资源作用域仍通过可信组合入口注入，不为八地点把基础模块堆成巨大 switch。

| 开场与进店     | 从街角/门头进入大堂，清楚交代旧店最后营业夜；开场可略过，不能伪造已读告示                         |
| 场景与人物融合 | 单舞台/单更新链；每地点有合适人物站位、遮挡、出口和声场；室内雨只在窗外，街道雨有深度             |
| 角色与表演     | Haru 默认、Miara 显式可选且资产完整；四态、三情绪、三种新动作单独可辨；人物动作不充当背景指标     |
| 探索顺序       | 海报→信件与信件→海报均成立，回访有变化；不强制搜集全部线索                                        |
| 信件与照片     | 旧海岸图没有人物；信封不等于正文；失败/取消后不泄露未读信息；已公开素材可以本地重读               |
| 三种结局       | 主动出发到街道、留信后门前告别、继续陪伴留一盏灯；背景、道具或灯光结果有可见差异                  |
| 拒绝与天气     | 不看照片也可离店并在合法节点看到雨势缓和；旧照片前置在所有层同步替换                              |
| 导航与打断     | 纯导航无需假音频；转场、读信、留信、翻牌、熄灯中都可被新输入打断；旧结果不污染新轮                |
| 失败与恢复     | 目标图失败保留原位置；音频失败可字幕/导航；重连恢复最后地点及事实，不重演历史或跳回初始座位       |
| 手机与无障碍   | 八地点热区与出口可触控/键盘访问；软键盘/旋转后坐标仍对齐；输入和打断可用                          |
| 连续体验       | 完整主线约 10–15 分钟；3–5 分钟精简路线经过至少五个独立背景，并包含聊天、视觉事件、打断与失败恢复 |

修改生命周期/协议需补测试源码：跨地点迟到/回滚、无语音呈现队列、地点与道具独立回执、旧冻结回执排序、未读信防泄露、结局多目标完成、拒绝照片后独立天气前置、旧角色加载与新实例交错。遵守 AGENTS.md，本稿与实施 prompt 均不新增功能、运行时或 E2E 执行授权，不运行含这些测试的 npm run check。

实施阶段按改动范围执行类型、lint、格式、构建、assets:check、webgal:check；契约变更生成 OpenAPI 并执行 contracts:check，使用项目固定 Node/npm launcher。手动浏览器视觉调试与测试套件分开记录，不调用付费 Provider 做探测，不把其他聊天的历史结果移作本轮证据。

## 14. v0.2 相对上一版的修订

本版将“三视图窗边陪伴”扩展为八个独立地点，补齐闭店夜的主线悬念、固定留言真相、可选探索、回访差异、三种行动结局和各地点制作要求。人物动作保留为表演基础，背景转换与场景状态另立目标。

相应增加了多地点导航、纯呈现事件、道具知识、灯牌状态与结局聚合的契约建议，并明确修订旧的照片→天气单线前置。复杂连续行走、坐站与握杯仍依资产评估，不阻碍通过背景、剪辑、道具与受控演出完成故事。
